# Local Contract Ledger Design

## Purpose

The local contract ledger is a SQLite-backed CLI system for grounding agent work
in explicit definitions of done. It turns completion from a prose claim into an
auditable contract with criteria, planned work, verifiers, receipts, disproof
attempts, and closeout rules.

The first version is local-only. It should work inside any repository without a
server, account, remote telemetry, or agent-specific API. Agents interact with it
through a CLI. Skills, `/goal`, and planning workflows teach agents when and how
to use the CLI, but the SQLite ledger remains the source of truth.

## Product Principles

- Done is a claim until receipts prove it.
- Contracts define done; todos describe a route toward done.
- Verifiers define acceptable evidence before work begins.
- Receipts record actual evidence after checks run.
- Closeout fails when criteria lack proof, deferral, or explicit residual risk.
- Accepted contracts can be amended, but amendments are recorded.
- Tool-specific proof should enter through verifier adapters, not hardcoded
  contract fields.
- Audit history should improve future templates, verifier choices, and task
  sizing.

## Scope

The ledger is designed for simple, atomic, modular tasks: the kind of unit that
can be generated by `/goal`, assigned to one agent, and closed in one work cycle.

A contract is right-sized when it has:

- one primary intent
- one owner or worker
- three to seven acceptance criteria
- three realistic disproof attempts for meaningful work, with explicit
  rationale when fewer are required
- verifiers from a small number of evidence domains

Larger initiatives should become parent goals with child contracts. For example,
`Prepare app for closed beta` is a goal; `Verify invite acceptance redirect`,
`Run authenticated billing E2E`, and `Compare onboarding redesign with Limner`
are contracts.

## Non-Goals

- No hosted service in v1.
- No remote telemetry in v1.
- No multi-user synchronization in v1.
- No attempt to replace issue trackers, project boards, or `/goal`.
- No model-specific runtime dependency.
- No requirement that the SQLite DB be committed to git.

## Workspace Shape

```text
.contracts/
  ledger.sqlite
  artifacts/
    <contract-id>/
      ...
  exports/
    <contract-id>.md
    <contract-id>-receipt.md
```

`ledger.sqlite` is canonical. Artifacts are local evidence files such as
screenshots, command logs, traces, JSON receipts, tool reports, DOM metrics, or
copied CI output. Exports are generated views for humans, PR descriptions, and
agent handoffs.

## Contract Model

A contract is the negotiated definition of done for one task. It is not just a
checklist. It captures what reality must look like for the work to count as
complete.

Core fields:

- `id`
- `goal_id` nullable
- `title`
- `intent`
- `scope`
- `non_goals`
- `assumptions`
- `status`
- `repo_path`
- `branch`
- `created_by`
- `created_at`
- `accepted_at`
- `started_at`
- `closed_at`

Recommended statuses:

- `draft`: editable contract before acceptance
- `accepted`: agreed contract, not yet active
- `active`: implementation or verification is underway
- `blocked`: progress requires user input or external state
- `closing`: closeout is being assembled
- `closed`: closeout passed
- `reopened`: closed contract was reopened after new evidence or failure
- `abandoned`: task was intentionally stopped

After a contract is accepted, changes to intent, scope, criteria, verifiers, or
closeout policy must be recorded as amendments with reasons.

Parent goals are optional grouping records. They organize multiple contracts but
do not replace contract closeout.

Goal fields:

- `id`
- `title`
- `intent`
- `status`
- `created_by`
- `created_at`
- `closed_at`

## Amendments

Amendments are explicit changes to accepted contracts. They prevent agents from
quietly moving the definition of done after discovering the task is harder than
expected.

Fields:

- `id`
- `contract_id`
- `reason`
- `changed_fields_json`
- `created_by`
- `created_at`

Every amendment also writes a `contract_amended` event.

## Criteria

Criteria are the structured definition-of-done checklist. Each criterion states
one truth that must hold at closeout.

Fields:

- `id`
- `contract_id`
- `statement`
- `required_evidence_kind`
- `priority`
- `status`
- `rationale` nullable
- `residual_risk` nullable
- `created_at`
- `satisfied_at`

Statuses:

- `pending`
- `satisfied`
- `failed`
- `deferred`
- `rejected`

Closeout requires every criterion to be `satisfied`, `deferred`, or `rejected`.
Deferred and rejected criteria require rationale and residual risk.

## Verifiers

Verifiers are the tools or evidence sources agreed in advance as acceptable
proof. They are distinct from implementation tools.

Verifier kinds:

- `command`: test, build, lint, script, migration check, CLI probe
- `browser`: browser inspection, screenshot, flow smoke, accessibility check
- `visual_fidelity`: screenshot, reference comparison, DOM metric, or design
  comparison workflow
- `diff`: direct code or doc diff inspection
- `ci`: CI status or hosted preview check
- `manual_inspection`: explicit human or agent inspection
- `external_link`: issue, PR, dashboard, trace, release, or hosted artifact
- `adapter`: tool-specific verifier backed by a registered adapter profile

Fields:

- `id`
- `contract_id`
- `criterion_id` nullable
- `adapter_id` nullable
- `name`
- `kind`
- `config_json`
- `required`
- `created_at`

Examples:

```sh
contract verifier add command "npm test -- billing" --for tests-pass
contract verifier add adapter limner --target billing-settings --mode reference-app --for ui-match
contract verifier add browser --url http://localhost:3000/settings/billing --for ui-visible
```

Closeout should prefer receipts from required verifiers. Replacing a required
verifier with weaker evidence after acceptance is an amendment.

## Verifier Adapters And Acceptance Profiles

The core ledger should not hardcode the behavior of individual tools such as
Limner, Playwright, Sentry, PostHog, billing sandboxes, migration checkers, or
custom project scripts. Instead, specific tools enter the system through
verifier adapters.

An adapter describes how a tool is configured, how it is run, what artifacts it
usually produces, and how its output should be mapped into receipts. An
acceptance profile is a reusable adapter configuration for a domain-specific
proof pattern, such as visual fidelity, analytics event verification, database
permission denial, or billing webhook replay.

Adapter fields:

- `id`
- `name`
- `version`
- `kind`
- `status`
- `config_schema_json`
- `artifact_patterns_json`
- `receipt_mapper_json`
- `requires_judgment`
- `created_at`
- `updated_at`

Acceptance profile fields:

- `id`
- `adapter_id`
- `name`
- `description`
- `status`
- `default_config_json`
- `default_required_artifacts_json`
- `default_failure_modes_json`
- `created_at`
- `updated_at`

The adapter interface should be intentionally small:

```text
input: verifier config + contract context
run: optional command or manual capture step
output: receipt status + summary + artifact paths + raw metadata
```

Adapters may classify a command run as `pass`, `fail`, or `inconclusive`, but a
successful command is not automatically proof that the criterion is satisfied.
Some adapters produce evidence that requires agent or human judgment before the
criterion can move to `satisfied`.

Limner should be a first-party example adapter, not a privileged database
concept. A Limner visual-fidelity profile can define:

- expected config: `target`, `mode`, `url`, `viewport`, `storage_state`, and
  `full_page`
- expected artifacts: screenshots, side-by-side image, DOM metrics, report, run
  manifest, and event log
- expected judgment: named mismatches, intentional deviations, and whether the
  visual criterion is satisfied, failed, or inconclusive

This keeps the ledger general while still making high-value tools easy for
agents to use correctly.

## Todos

Todos are implementation plan items. They help agents navigate the work but do
not by themselves prove completion.

Fields:

- `id`
- `contract_id`
- `title`
- `description`
- `status`
- `linked_criterion_id` nullable
- `claimed_by`
- `created_at`
- `completed_at`

Statuses:

- `pending`
- `active`
- `done`
- `blocked`
- `dropped`

Todos can be linked to criteria, but criteria remain the closeout gate.

## Receipts

Receipts are first-class evidence records. They answer: what was checked, how was
it checked, what happened, and where is the durable artifact?

Tables:

```text
receipts
  id
  contract_id
  criterion_id nullable
  verifier_id nullable
  todo_id nullable
  disproof_attempt_id nullable
  kind
  status
  summary
  command nullable
  exit_code nullable
  stdout_excerpt nullable
  stderr_excerpt nullable
  adapter_metadata_json nullable
  content_hash nullable
  created_by
  created_at

artifacts
  id
  contract_id
  path
  mime_type
  size_bytes
  sha256
  created_at

receipt_artifacts
  receipt_id
  artifact_id
```

Receipt statuses:

- `pass`
- `fail`
- `inconclusive`

Receipt commands:

```sh
contract receipt run --criterion tests-pass --verifier unit-tests
contract receipt add --criterion tests-pass --command "npm test -- billing" --status pass
contract receipt attach --criterion visual-proof --file ./screenshot.png --kind screenshot
contract receipt list
contract receipt show receipt-12
```

Where possible, the CLI should run verifiers directly and capture stdout,
stderr, exit code, timestamps, and artifact hashes. Manual receipts are allowed
but should be auditable and easy to flag when stronger verifiers were available.

## Disproof Attempts

A disproof attempt names a realistic way the work could still be wrong and
records the check used to test that fear.

Fields:

- `id`
- `contract_id`
- `failure_mode`
- `why_plausible`
- `linked_criterion_id` nullable
- `check_description`
- `expected_verifier_id` nullable
- `expected_proof_json`
- `resolution_rule`
- `status`
- `required`
- `fewer_than_default_reason` nullable
- `residual_risk`
- `created_at`
- `resolved_at`

Statuses:

- `pending`
- `ruled_out`
- `confirmed`
- `inconclusive`
- `accepted_risk`

Closeout should require at least one disproof attempt for trivial contracts.
Meaningful contracts should default to three realistic disproof attempts.
High-risk contracts should require three disproof attempts plus at least one
negative or adversarial check. If fewer than three disproof attempts are used for
meaningful work, the contract must record why that is acceptable.

## Agent Failure Mode Interface

Agents should read failure modes as a falsification queue, not as loose notes.
The CLI should expose the queue in a compact human view and a structured JSON
view.

Example read payload:

```json
{
  "contract_id": "ctr_123",
  "intent": "Match onboarding redesign to approved reference",
  "failure_modes": [
    {
      "id": "fm_1",
      "statement": "Desktop layout matches but mobile breakpoint is broken",
      "why_plausible": "The implementation changed responsive grid behavior.",
      "linked_criteria": ["visual-mobile"],
      "required": true,
      "status": "pending",
      "expected_proof": {
        "verifier": "visual-fidelity-mobile",
        "kind": "visual_fidelity",
        "artifacts_required": ["side-by-side", "dom-metrics", "report"]
      },
      "resolution_rule": "Attach passing receipt or record accepted residual risk."
    }
  ]
}
```

When agents write failure modes, they must provide:

- the failure hypothesis
- why it is plausible
- the criterion it threatens
- the verifier or proof source expected to rule it out
- the artifacts or observations required
- whether it is required for closeout
- final status and residual risk when resolved

This makes a failure mode an auditable risk claim with a proof obligation.

## Events And Audit Trail

Every CLI invocation and every meaningful mutation writes audit data. The event
audit log lives inside the same `ledger.sqlite` database as contracts, criteria,
verifiers, receipts, todos, adapters, acceptance profiles, and amendments.
Generated Markdown exports are views of this state, not the audit source of
truth.

The audit model has two layers:

- `command_invocations` records every CLI use, including read-only commands such
  as `contract status`, `contract adapter list`, and
  `contract failure-modes list`.
- `events` records state changes and important lifecycle moments caused by those
  commands.

`command_invocations` fields:

- `id`
- `actor`
- `session_id` nullable
- `contract_id` nullable
- `scope_type`
- `scope_id` nullable
- `command`
- `subcommand` nullable
- `argv_json`
- `cwd`
- `started_at`
- `completed_at` nullable
- `exit_code` nullable
- `status`

The CLI should redact known secret-bearing values before storing `argv_json`.
Examples include tokens, passwords, cookies, API keys, auth headers, and storage
state contents. The audit log should record that a secret-like value was present
without storing the value.

`events` fields:

- `id`
- `command_invocation_id` nullable
- `contract_id` nullable
- `scope_type`
- `scope_id` nullable
- `actor`
- `event_type`
- `payload_json`
- `created_at`

Important event types:

- `cli_invoked`
- `cli_completed`
- `contract_created`
- `contract_accepted`
- `contract_started`
- `contract_amended`
- `criterion_added`
- `criterion_status_changed`
- `verifier_added`
- `verifier_updated`
- `verifier_removed`
- `verifier_run_started`
- `verifier_run_completed`
- `verifier_run_failed`
- `adapter_registered`
- `adapter_updated`
- `adapter_disabled`
- `adapter_invoked`
- `adapter_completed`
- `adapter_failed`
- `profile_registered`
- `profile_updated`
- `profile_disabled`
- `todo_added`
- `todo_status_changed`
- `receipt_created`
- `artifact_attached`
- `failure_mode_added`
- `failure_mode_status_changed`
- `closeout_attempted`
- `contract_closed`
- `contract_reopened`
- `export_created`
- `audit_run`

Adapter usage should produce both command-level and lifecycle-level audit data.
For example, `contract receipt run --verifier limner-reference-app` should log
the CLI invocation, verifier run start, adapter invocation, discovered artifact
paths and hashes, adapter completion or failure, receipt creation, and artifact
attachment. Registering or changing an adapter or profile should log both the CLI
invocation and the adapter/profile event.

The event stream supports audits, retrospectives, and future migrations without
trusting generated Markdown.

## CLI Lifecycle

Draft and accept:

```sh
contract init "Fix billing settings regression"
contract criteria add "Canceled users cannot access premium export" --requires command
contract verifier add command "npm test -- billing" --for canceled-export
contract todo add "Add regression test for canceled subscription state"
contract accept
```

Work:

```sh
contract status
contract failure-modes list --json
contract todo claim todo-3
contract todo done todo-3
contract verify canceled-export
contract receipt list
```

Disprove and close:

```sh
contract failure-modes add \
  --failure-mode "Checkout still works in tests but fails for canceled users in browser"

contract receipt run --failure-mode fm_1 --verifier billing-e2e
contract failure-modes resolve fm_1 --status ruled_out --receipt receipt-7
contract close
```

Export:

```sh
contract export --format md
contract receipt export --pr
```

## Closeout Rules

`contract close` should fail unless:

- the contract is accepted or active
- every required criterion is satisfied, deferred, or rejected
- satisfied criteria have at least one passing receipt
- deferred or rejected criteria include rationale and residual risk
- required verifiers have receipts or an amendment explains why they were not
  used
- required disproof attempts are resolved or accepted as residual risk
- meaningful contracts have three disproof attempts unless fewer are justified
- blocked todos are either linked to residual risk or moved into follow-up
  contracts

The closeout command should emit a concise final receipt:

```text
Claim: <what is complete>
Receipts: <receipt ids and summaries>
Disproof attempts: <failure modes and results>
Residual risk: <none, follow-up, or accepted risk>
```

## Goal And Skill Integration

The CLI is canonical. Integrations should make agents use the CLI rather than
becoming parallel sources of truth.

Recommended integration layers:

1. A `contract-ledger` skill that instructs agents to draft, accept, update, and
   close contracts through the CLI.
2. `/goal` integration that creates one parent goal and one contract per atomic
   task.
3. Planning-session integration that ends plans by creating contract drafts with
   criteria, verifiers, and todos.
4. Worker-prompt integration that passes contract IDs instead of informal task
   descriptions.

Example worker handoff:

```text
Work contract: ctr_123.
Start by running `contract status ctr_123`.
Use the contract todos to guide implementation.
Do not claim completion until `contract close ctr_123` passes.
```

The integration mantra is:

```text
Plans create contracts.
Contracts create todos.
Verifiers create receipts.
Receipts permit closeout.
Audits improve the next contract.
```

## Audits And Retrospectives

Audit commands should help improve the contract system over time.

Commands:

```sh
contract audit contract ctr_123
contract audit recent
contract audit weak-closeouts
contract audit amendments
contract audit verifier-health
contract audit adapter-usage
contract audit command-usage
contract audit patterns --since 30d
contract audit retro --since 7d
```

Weak closeout flags:

- criteria closed without receipts
- manual inspection used when stronger required verifiers existed
- accepted contracts amended without clear reasons
- meaningful contracts closed with fewer than three failure modes and no
  rationale
- adapter or profile changes without corresponding audit events
- verifier runs without adapter lifecycle events when an adapter is used
- receipt artifacts missing hashes or discovered-path metadata
- todos marked done without advancing linked criteria
- residual risk recorded without a follow-up contract
- failed verifier replaced by weaker evidence
- contract reopened after closeout

Retrospectives should summarize recurring patterns and suggest changes to
templates, skills, verifier defaults, and task sizing.

## Risks

- Agents may bypass the CLI and write convincing prose. Mitigation: skills and
  prompts must require contract IDs and closeout receipts.
- Contracts may become too large. Mitigation: audit large criteria counts,
  unrelated verifier domains, and repeated amendments.
- SQLite state may be ignored in PRs. Mitigation: export Markdown receipts for
  handoff and PR descriptions.
- Manual receipts may become a loophole. Mitigation: audit manual-only closeouts
  when required verifiers existed.
- Adapter profiles may drift from the tools they wrap. Mitigation: adapter
  health audits should run sample verifiers and flag stale artifact mappings.
- Usage logging may collect sensitive command arguments. Mitigation: redact
  secret-like values before writing invocation records.
- Required verifiers may be wrong or too expensive. Mitigation: amendments are
  allowed but recorded with reasons.

## V1 Success Criteria

- An agent can create and accept a contract before implementation.
- The CLI stores contract, criteria, verifiers, todos, receipts, disproof
  attempts, artifacts, command invocations, and events in SQLite.
- The CLI can list built-in verifier adapters and acceptance profiles.
- The CLI can register and update verifier adapters and acceptance profiles.
- The CLI can run command verifiers and record receipts.
- The CLI logs adapter registration, profile changes, adapter invocation,
  verifier runs, receipt creation, and artifact attachment.
- The CLI can attach file artifacts with hashes.
- `contract close` blocks weak closeout according to explicit rules.
- The CLI can export a readable Markdown contract and receipt.
- Audit commands can identify weak closeouts, amendments, and verifier health.
- A skill or prompt template can guide an agent through the workflow using only
  the CLI.
